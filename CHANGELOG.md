## [Unreleased]

### Security

* **Firestore `user` collection queries now carry their account scope as a filter instead of only an ordering, so a project can deny unscoped listing.** Firestore evaluates a `list` operation by matching the rule against the query's **filters**; `request.query` exposes only `limit`, `offset`, and `orderBy`. An `orderBy` does restrict which documents are returned — Firestore omits documents that lack the ordered field — but a rule cannot *require* it, so a `list` rule cannot distinguish a legitimate ordered read from an enumeration of the entire collection. The practical consequence is that a project **cannot tighten `list` on a collection at all** while any client still issues an unfiltered query against it: the tightened rule would break the legitimate screen while the attacker simply reissues the same query. Because the queries live in this package rather than in the application, the fix has to land here before any consuming project can close the gap.
  * **New `UserQuery` helper (`lib/helper/user_query.dart`).** The single place that builds `user` collection queries. `UserQuery.scopeToField` applies the `where` filter together with the matching lead ordering, because Firestore requires an inequality field to be the first ordering and a caller applying only one half gets either a runtime error or an unscoped read. `UserQuery.byGroup` scopes by group identifier, `UserQuery.isScoped` reports whether a query is constrained to an account by inspecting its **filters** rather than its ordering, and `UserQuery.collection` returns a `CollectionReference` so callers can reach a single document. Exported from `package:fabric_flutter/fabric_flutter.dart`.
  * **`UserAdmin` and `UserRolesFirebase.getUsers` scope group listings with a filter.** A group listing now carries `groups.<group> != null` (`UserAdmin`) or `roles.<group> != null` (`UserRolesFirebase.getUsers`) alongside the ordering it already applied. **The returned documents are unchanged** — Firestore already omitted documents lacking the ordered field — but the constraint is now something a `list` rule can match against. `UserAdmin`'s query construction is exposed as `resolveUserAdminQuery` so the scoping decision can be asserted without mounting the widget.
  * **Both listing entry points accept a caller-supplied query.** `UserAdmin(query: ...)` and `UserRolesFirebase.getUsers(query: ...)` replace the collection reference the package would otherwise build, so a project whose rules deny unscoped `list` can pass a query it has already narrowed. Ordering, group scoping, and `limit` are applied on top; the package never widens what the caller supplied.
  * **`StateUsers` batched lookups are now `get` operations, not a `list`.** `StateUsers.fetchUsersById` previously resolved a batch with `where(FieldPath.documentId, whereIn: uids)`, which is a **`list`** operation. It now issues concurrent `doc(uid).get()` reads, which are **`get`** operations governed by a separate rule. This lets a project keep `allow get` open for the users a caller may legitimately resolve while denying `allow list` on the collection outright. Billed document reads are unchanged (both forms bill one read per returned document) and the batch still resolves in roughly one round trip. Documents that do not exist are omitted, matching the previous `whereIn` behaviour. `StateUsers.whereInLimit` keeps its name and value (30) for API compatibility but now bounds read concurrency rather than satisfying a query restriction.
  * **Unscoped, collection-wide reads remain the default when no group and no query are supplied**, deliberately: removing them would break consumers that pin this package. Those paths require the consuming project to permit unscoped `list`. Prefer passing `group` or `query`.
* **Untrusted URLs are validated against a scheme allow-list before reaching a platform handler (`lib/helper/url_safety.dart`).** `ExpansionTable`, `JsonExplorerSearch`, and `GoogleChartContainer` render values they did not author — table cells, decoded JSON, chart links — and passed them to `launchUrl`/`launchUrlString` after nothing stronger than a parse. `Uri.parse` is not validation: it succeeds for `javascript:alert(1)` and for `file:///etc/passwd`, and the `hasAbsolutePath` check previously used by `JsonExplorerSearch` accepts both `file:///…` and `javascript:/x`. The new `UrlSafety` helper enforces an `https`/`http` allow-list plus a non-empty host (an allow-list, not a denylist, because a denylist is correct only until a platform adds another scheme), and the three widgets now render a value as tappable only when it passes. Exported from `package:fabric_flutter/fabric_flutter.dart`.
* **The APNS device token is no longer written to release logs.** `StateNotifications` logged the resolved APNS token through an unguarded `debugPrint`, which is **not** stripped from release builds. A push token is a bearer credential for delivering to a device. It now logs only that a token resolved, and only under `kDebugMode`.

#### Breaking-change assessment

**None of the above is a breaking change.** All new parameters are optional, all new API is additive, and no existing signature changed:

* Group listings return the **same documents** as before, because the added `!= null` filter selects exactly the set the existing `orderBy` already produced.
* `StateUsers.fetchUsersById` keeps its signature and its `@protected @visibleForTesting` override point; only the implementation changed. Tests that override it are unaffected.
* `StateUsers.whereInLimit` and `StateUsers.chunkUids` keep their names, values, and behaviour.

**Consumer migration — opting into scoped listing.** No change is required to keep working. To let a project deny unscoped `list` on the user collection, supply a scope:

```dart
// Before — ordered only; indistinguishable from an enumeration to a `list` rule.
UserAdmin();
await UserRolesFirebase.getUsers();

// After — scoped by group, or by a query the project has already narrowed.
UserAdmin(group: 'acme');
UserAdmin(query: myScopedQuery);
await UserRolesFirebase.getUsers(group: 'acme');
await UserRolesFirebase.getUsers(query: myScopedQuery);
```

Projects that pin this package by exact commit must bump the pin before the rule change takes effect in production.

**Known inconsistency, left unchanged deliberately.** `UserRolesFirebase.getUsers` scopes on `roles.<group>` while `UserAdmin` and `UserRoles.roleFromData` use `groups.<group>`; `UserData.roles` is a `List<String>` and `UserData.groups` is a `Map<String, String>`. Each call site was scoped on the field it already ordered by so that a security change did not silently alter a result set. Reconciling the two belongs in a separate, clearly-labelled change.

**Documented as consumer responsibilities** rather than changed here, because changing them would break existing consumers: `IframeMinimal` on native enables unrestricted JavaScript and permits every navigation request, so its `src` must be trusted content; `FirebaseStorageHelper` reads and writes Cloud Storage objects directly with no application logic in between, so path, content type, size, and read access are governed only by the project's Storage rules; and client-side role checks (`StateUser.admin`, `StateUser.accessByRole`, `UserRoles.roleFromData`) decide what to render and are never an authorization decision.

### Fixed

* **`StateUser.serialized` and `StateUsers.serialized` now expose a non-deduplicated `hadSerializationError` flag.** When JSON deserialization fails (e.g. an enum field receives an unknown value), the state sets `error` and returns a fallback value. The `error` setter uses dedup logic to avoid notifying listeners repeatedly for the same error, which is efficient but creates an observability gap: if deserialization fails identically on repeated reads, the error is reported once (from a callback) and then silently swallowed. A `hadSerializationError` bool flag is now set fresh on every read, independent of dedup, so consumers can reliably detect every failure. The flag is reset at the start of each `serialized` getter so it reflects the current state, not a stale value from a previous successful read. **This is a consumer-visible change:** code that checks `error` is unaffected, and code that reads `hadSerializationError` gains observability; the fallback value and the error message are unchanged.
* **`StateUsers.getUser` now retries lookups after network failures.** When `fetchUsersById` fails (e.g. a transient network error), failed UIDs are tracked in a `_failedUids` set. On the next call to `getUser` for a failed UID, the cached placeholder is discarded and the UID is re-enqueued for fetch, allowing retry. Documents that genuinely do not exist (present in Firestore query results but without data) are not marked as failed and are not retried. **This is a consumer-visible change:** code that calls `getUser` with a network-error UID on the second attempt now triggers a retry instead of returning a stale placeholder; the batching, dedup, and public API are unchanged.

### Added
* **`GoogleMapsSearch` now supports an injectable HTTP client factory.** Pass `clientFactory` to use a custom transport for autocomplete and place-details requests. The widget creates one client per mounted state, reuses it for both request types, and closes it on disposal; omitting the factory preserves the standard `http.Client` behavior.
* **Agent Bridge transports, authentication gate, and audit log — an external agent can now connect to a running application over a real channel, prove who it is, and leave a trail.** This layer sits on top of the transport-agnostic Agent Bridge core (below) and changes nothing about it: all access control is implemented as an `AgentAuthorizer`, and every transport funnels through one dispatcher, so a new transport cannot widen the attack surface by accident. It adds **no new dependencies** and is **inert until a host explicitly turns it on twice** — once with `AgentBridge.instance.configure(enabled: true, ...)`, and once by starting a transport.
  * **Three transports behind one entry-point shape.** `AgentBridgeServer.start({options, bridge, verifier, principals, auditSink, requireAuthenticationForDiscovery})` / `stop()` resolves through the repository's conditional-import idiom: on **native** (desktop, mobile) it binds a `dart:io` `HttpServer` that serves both a WebSocket upgrade (one JSON request per text frame) and `POST` (one JSON request per body) on the same port; on **web** — where a page cannot listen on a socket — the transport is inverted and a callable `window.fabricAgentBridge(request)` is installed via `dart:js_interop`, so Playwright, Puppeteer, a CDP client, an extension, or the console can drive the app. `AgentInProcessTransport.start(...)` mirrors the same signature for tests, embedded automation, and hosts that already own a channel (a platform channel, an MCP stdio server, a callable function), so a host can swap transports without changing its bootstrap. Every transport decodes JSON into a map, calls `AgentBridge.handle`, and encodes the result: **a malformed, non-object, or oversized payload always produces a well-formed `invalid_params` response and never an unhandled exception or a dropped connection**.
  * **Bearer token gate that reuses the existing OAuth flow and invents nothing.** The bridge implements **no login, token minting, or token refresh**. An agent obtains a normal OAuth 2.0 access token through the host's existing authorization-code flow and presents it in the reserved **`params.auth`** field of the request envelope (the `Bearer ` prefix is optional and case insensitive). `params.auth` is stripped before dispatch and is never passed to command handlers, which continue to receive only `params.params`. The native transport additionally accepts an `Authorization: Bearer` header or a `?token=` query parameter — browsers cannot set headers on a WebSocket handshake — and normalizes either into the same field, so the authorizer has exactly one place to look; an envelope token always wins, which lets one connection act for several principals. Verification is delegated to the host through `typedef AgentTokenVerifier = FutureOr<AgentPrincipal?> Function(String token)`, keeping `fabric_flutter` agnostic of Firebase or any particular backend; returning `null` or throwing denies the request, and the reason is never echoed to the caller.
  * **`AgentTokenAuthorizer`.** A real `AgentAuthorizer` that resolves the token through `AgentPrincipalResolver` — an LRU + TTL cache (5 minutes, 128 entries by default) that **never caches a rejection** and re-verifies on expiry, so a revoked token stops working promptly without a verifier call per request — denies with `unauthorized` when the token is missing, invalid, or expired, and enforces `AgentCommand.requiresRole` against the principal. The default role check passes `admin` unconditionally (`superRole`), then an exact role match, then a `<group>-<role>` requirement resolved against `AgentPrincipal.groups` (with a group `admin` passing), then a bare requirement held in any group; a custom `roleCheck` replaces those rules entirely. On approval the resolved principal is forwarded to the handler through `AgentAuthorization.allow(meta: ...)` under the keys `principal`, `principalId`, `role`, and `groups`. Because `command` is `null` for `ping` and `describe`, **discovery is gated independently** through `requireAuthenticationForDiscovery` and `requireAuthenticationForState` (both `true` by default), so a host can expose an anonymous capability listing without exposing execution — or, by default, expose nothing at all.
  * **Safety controls, restrictive by default.** A global kill switch (the core's `enabled` flag; every request answers `disabled` until a host opts in), loopback-only binding (`127.0.0.1`), port `8757`, a 64 KiB maximum request size, at most 4 concurrent connections, and a sliding-window rate limit of 60 requests per minute bucketed per principal (or per connection while anonymous), all tunable through `AgentBridgeServerOptions` (`copyWith` included). Oversized bodies answer `413`, excess connections `503`, and a non-`POST` method `405`. **Starting a transport throws an `ArgumentError` while the bridge is disabled, and throws when no verifier is supplied while the bridge still carries the permissive `AgentAllowAllAuthorizer`** (unless `requireAuth: false` is passed explicitly), so a transport can never exist ahead of the kill switch and shipping an unauthenticated bridge has to be a deliberate, visible act rather than an omission. This matters most on the web, where the transport installs a callable `window` property: a release build that never called `configure(enabled: true)` has no such property at all.
  * **Redacting audit log.** Every `invoke` — successful or not — emits one `AgentAuditRecord` (`timestamp`, `requestId`, `principalId`, `commandId`, `outcome`, `durationMs`, `params`, `errorCode`, `transport`) to an injectable `AgentAuditSink`, so hosts can forward it to Firestore, a log pipeline, or an analytics collector; `principalId` is `anonymous` when the caller presented no verifiable token, and a sink that throws is caught and reported so auditing can never fail a request. **Parameter values are never recorded**: each value is replaced by a type and size summary (`<string:3>`, `<num>`, `<bool>`, `<list:2>`, `<map:1>`, `<null>`), and a credential-shaped key (`auth`, `token`, `accessToken`, `refreshToken`, `idToken`, `password`, `apiKey`, `secret`, … matched case-insensitively with `_`, `-`, and `.` removed) becomes `<redacted>` with no size at all, so **not even a token's length leaks**. `describe`, `state`, and `ping` are not audited because they mutate nothing. Redaction, and the absence of any token substring anywhere in the emitted records, is covered by tests.
  * **New serialized models.** `AgentPrincipal` (`id`, `role`, `groups`, `scopes`, `expiresAt`, `claims`, plus `isExpired` and `roleInGroup`) and `AgentAuditRecord` with `AgentAuditOutcome`, both null-tolerant and exported from `package:fabric_flutter/fabric_flutter.dart` alongside `AgentAuditLog`, `AgentBridgeServer`, `AgentBridgeServerOptions`, `AgentDispatcher`, `AgentPrincipalResolver`, `AgentRateLimiter`, `AgentTokenAuthorizer`, and `AgentTransport`.
  * **Documented exposure model.** `docs/agent-bridge-protocol.md` carries a threat model (loopback-only default and why `0.0.0.0` is a bad idea, that the token is the only thing between a local process and full app control, that `enabled` belongs behind a remote flag rather than a compile-time constant, that the verifier is the revocation point, and that client-side role checks remain a blast-radius control rather than a security boundary) and a web exposure model stating plainly that `window.fabricAgentBridge` is reachable by any script in the page and is bounded by exactly three guarantees: the property exists only after a successful `start(...)`, `stop()` deletes it, and with the defaults an unauthenticated caller is refused on **every** method — `ping`, `describe`, `state`, and `invoke` all answer `unauthorized` and disclose neither the command catalog, the parameter schemas, the `requiresRole` values, the route list, the application name, nor any on-screen value, so a page script without a token cannot even enumerate capabilities. One known, accepted leak is documented: `invoke` with an unknown command answers `not_found` before authorization, so command identifiers are guessable.
  * **Documentation and an end-to-end test.** The wire protocol, the envelope, where the bearer token belongs, the authorization rules, the safety table, the audit shape and redaction guarantees, all three transports, and a host bootstrap snippet are specified in [`docs/agent-bridge-protocol.md`](docs/agent-bridge-protocol.md) and summarized in the README. An integration test drives a small sample application through the in-process transport end to end — authenticate, `describe`, `state`, `set_value`, `wait_for`, `tap`, `navigate` — and asserts the unauthorized and insufficient-role paths, the audit ordering and attribution, and that no token appears in any record.
* **Agent Bridge core — external agents can now discover and drive an application the way a user can.** A new, self-contained layer under `lib/helper/agent/` exposes a JSON-RPC-shaped, MCP-friendly protocol so an autonomous agent (Claude, an MCP client, a cloud workflow) can read the current screen, set any input, tap any button, navigate anywhere, and run host-registered actions. The layer is **transport agnostic and performs no access control**: `AgentBridge.handle` takes a decoded request map and returns a decoded response map, which lets a socket server, a JavaScript interop entry point, or an in-process test drive it without any protocol change. It is **disabled by default** — every request answers with the `disabled` error until a host calls `AgentBridge.instance.configure(enabled: true, ...)` — and it adds **no new dependencies**.
  * **Protocol.** Requests are `{ "id", "method": "describe" | "state" | "invoke" | "ping", "params": {...} }`; responses are `{ "id", "ok": true, "result": {...} }` or `{ "id", "ok": false, "error": { "code", "message" } }` with the error taxonomy `unauthorized` / `not_found` / `invalid_params` / `disabled` / `failed`. `describe` publishes `{ app, version, routes, commands }` and is shaped to map 1:1 onto MCP tool definitions, so a remote MCP server can wrap it later without a protocol change.
  * **Capability registry.** `AgentRegistry` (`register`, `registerAll`, `unregister`, `contains`, `byId`, `byCategory`, `withCategory`, `catalog`, `clear`) stores `AgentCommand`s — a serializable `AgentCommandInfo` paired with a handler that never crosses the transport boundary. Registering a duplicate identifier throws unless `override: true` is passed. Host applications register their own domain commands into the same registry, and a host may specialize a built-in by registering its own version *before* calling `configure`, which never overwrites an existing identifier.
  * **Built-in commands.** `navigate`, `set_value`, `tap`, `read_value`, `wait_for`, `screen_state`, and `list_commands`. `wait_for` polls a condition (`visible`, `absent`, `enabled`, `disabled`, `value`, or a route match) until it holds or its timeout elapses, so an agent can synchronize without polling screenshots. Every `invoke` runs under a timeout (30s by default, shortened per request with `timeoutMs`).
  * **Live element index.** Keyed widgets publish themselves to `AgentElementIndex` on mount, refresh on rebuild, and remove themselves on dispose, exposing `{ id, type, label, hint, value, enabled, visible }` plus an optional setter and activator. **The existing accessibility metadata is reused as the agent-facing contract** — `automationKey` is the identifier, `semanticsLabel` the label, `semanticHint` the description — so there is no parallel metadata to maintain. `InputData`, `SmartButton`, `CardButton`, and (through `InputData`) `UsersDropdown` are wired. The binding widget `AgentElement` adds **no `Semantics` node, no layout, and no rendering change**, and registers nothing at all when the identifier is absent, so the accessibility tree and the widget tree are byte-for-byte unchanged and wrapping an unkeyed widget is free. `set_value` drives an input exactly as user input would, including validation and listener notification; for date, time, and selection inputs it parses the JSON value and resolves options by value, identifier, name, or label rather than opening a platform picker.
  * **Authorization seam.** The core deliberately ships **no** authentication. `AgentBridge.configure(authorizer: ...)` accepts an `AgentAuthorizer`, which receives the decoded request and the resolved command — including its `requiresRole` — and returns an `AgentAuthorization`. The default `AgentAllowAllAuthorizer` approves everything. An approving decision may attach `meta`, which is forwarded to the command handler through `AgentCommandContext.meta`, so a future authentication layer can pass the resolved principal or role claims down without changing a single signature.
  * **Serialized models.** `AgentParam`, `AgentCommandInfo`, `AgentRouteInfo`, `AgentElementSnapshot`, `AgentRequest`, `AgentError`, `AgentResponse`, `AgentDescribeResult`, and `AgentStateResult`, all null-tolerant and exported from `package:fabric_flutter/fabric_flutter.dart` alongside the helper layer.
  * Hosts that expose the bridge beyond a trusted process **must** replace the default authorizer, and should attach `AgentNavigatorObserver.instance` to `MaterialApp.navigatorObservers` and `AppGlobal.navigatorKey` to `MaterialApp.navigatorKey` so route reporting and `navigate` work.

### Fixed
* **`StateDocument.revert()` now leaves edit mode reliably, including when nothing was edited.** `revert()` clears the `edit` flag and then restored the snapshot through `data = snapshot` as its only notification. But `copy` is a `Map.from(data)` taken when editing began, so cancelling an edit that changed nothing hands the `data` setter a *fresh but structurally equal* payload — exactly the case the setter deliberately suppresses. The flag flipped to `false` and no listener ever heard about it, leaving views bound to `edit` stuck in edit mode after a cancel. `revert()` now notifies unconditionally, because `edit` is state the `data` setter knows nothing about and cannot be responsible for publishing.
  * **This one is a genuine regression**, unlike the aliasing defects below. At `99ab64e` the guard compared with `==`, which is *referential* for `Map`, so a fresh snapshot never matched it and the notification always fired. The deep structural comparison introduced in #221 is what began suppressing it. Note that `revert()` itself arrived later, in #222, so the broken behaviour only appears where both changes are present.
  * Measured, as notifications delivered by the cancel action:

    | Scenario | `99ab64e` | after #221 | after this fix |
    |---|---|---|---|
    | Cancel **without** editing anything | 1 | **0** | 1 |
    | Cancel after editing a field | 1 | 1 | 2 |

  * **The #221 optimisation is untouched.** The setter's structural comparison is unchanged — the bottom row is identical before and after — and the fix only stops `revert()` depending on that comparison to publish an unrelated state change.
  * **The `2` is deliberate:** reverting an edit that *did* change a field notifies once from the `data` setter and once from `revert()`. The debounce coalesces those into a single rebuild outside of tests, and a redundant rebuild is the right trade for never missing the edit-mode exit. The existing test asserting a single notification was updated to pin the new count.
  * The suite missed this because every pre-existing `revert()` test changed a field first, which is the path that still worked. The no-op cancel is now covered.
* **`StateShared.data` notifies again when the assigned payload is the object the state already holds, and `StateShared.merge` no longer mutates the list it was given.** `privateData` and `privateOldData` reference the *same* instance, so the value under comparison and the baseline it is compared against are one object. Anything mutated in place is therefore already reflected in the baseline, and the guard in the `data` setter could only ever conclude "unchanged" — the notification was dropped, and no listener rebuilt. `merge()` made this reachable from inside the package: it started with `List<dynamic> newData = base;` (no copy), mutated, and returned `base`, while its callers do exactly `data = merge(base: data, toMerge: ...)` (`state_api.dart`, both the incremental-pagination path and the chunked-stream path). The setter now treats a same-instance assignment as changed rather than as identical, and `merge()` copies before mutating, so `base` is left intact and stays usable as a comparison baseline. The setter also drops any value memoized through `cachedSerialize`, which keys on `identical()` and so cannot detect a same-instance reassignment on its own — this is what left `StateUser.serialized` returning a stale `UserData` after an in-place edit.
  * **These are pre-existing latent bugs, not a regression from the `DeepCollectionEquality` change in #221.** Verified by direct comparison against `99ab64e`, the last version known to work in a consuming application, where the guard read `privateOldData == dataObject` — and `==` is *referential* for `Map` and `List`, so a same-instance reassignment was dropped there too — and where `merge()` already read `List<dynamic> newData = base;`. Both defects predate that commit. **This does not claim to explain any particular report of a state class not notifying**; it closes two demonstrable holes and adds the regression tests that should have caught them.
  * **Deduplication of structurally-equal *fresh* payloads is deliberately preserved.** A brand-new `Map` or `List` that deep-equals the current value is still ignored, so the rebuild reduction from #221 is intact and is now pinned by a test.
  * **Behavioural change worth auditing: a listener that reassigns `data` unconditionally now recurses without bound.** The previous guard compared references, so `state.data = state.data` from inside a listener was swallowed silently; it now notifies, re-enters the setter, and notifies again. Measured: under `flutter test`, where notification is synchronous, this overflows the stack, and the `StackOverflowError` is reported through `FlutterError` rather than thrown where a `try`/`catch` around the assignment could contain it; in a release build the debounce turns the same pattern into an endless timer loop that rebuilds forever instead of crashing. Nothing in this package does this. A listener that writes back to `data` must first check that the value actually needs changing.
  * **Behavioural change worth auditing: `merge()` no longer mutates its `base` argument.** It is a public method on an exported class. Every call site inside this package assigns the return value and is unaffected, but a consumer that called `merge(base: myList, ...)` and then read `myList` expecting it to have been updated in place must now read the returned list instead. The copy is shallow — entries are shared, which is sufficient because merging replaces and appends elements without mutating one — and adds no complexity class, since building the `indexById` map was already `O(base)` per call.
  * **Known limitation, unchanged:** a consumer that mutates `data` in place and *never* reassigns still poisons the comparison baseline, so a later fresh payload that deep-equals the mutated value is still deduplicated. Closing that would require an unaliasable baseline — a deep copy or a fingerprint captured at assignment time — at the cost of the #221 optimisation. After this fix no path inside this package mutates the baseline; assign a copy, as `StateDocument.editField` does.
  * **Known test gap, reported but not changed here:** `kIsTest` (`lib/variables.dart`) makes both `notifyListeners()` and `_notifyData()` return before the debounce path under `flutter test`, so any defect living in the debounce logic is structurally invisible to the current suite. The debounce code is untouched by this change.
* **`SmartButton` now fires `ButtonOptions.onTap` on buttons that have an `onTap` and no `path`.** Activation ran the callback only as a side effect of navigating, so a button configured with `onTap` alone rendered as enabled, focusable, and announced as actionable — but pressing it did nothing. `onTap` is now always invoked, and navigation still follows exactly as before when a `path` is present (including the `pop: true` replace behavior). **This is a behavioral change on upgrade:** any existing `ButtonOptions(label: ..., onTap: ...)` without a `path` was silently inert and will now run its callback, which matters most for destructive actions such as remove or delete confirmations. No call site should need to change — nobody writes an `onTap` expecting it to be ignored — but audit tap-only buttons whose callbacks were never actually reached. The fix also makes such buttons reachable through the agent bridge's `tap` command, which would otherwise have been a no-op. Covered by regression tests asserting `onTap` fires when `path` is `null`, that the `path` and `pop` behavior is unchanged, and that a button with neither remains inert.

### Accessibility
* **`CardButton` is announced as a single button.** The card previously published a plain container node, so screen readers read the image placeholder, the headline, and the description as separate, unlabeled fragments and never announced the card as actionable. The card now renders one `Semantics` node with `button: true`, the tap action, and a single label; the decorative background image is excluded from the semantics tree (`SmartImage.excludeSemantics`), and the overlay text is excluded because it is already carried by the node's label — so the whole card is announced exactly once. When `semanticsLabel` is omitted the label is derived from the visible content (`headline` and `description` joined into one sentence) instead of only `headline`, so **existing call sites get a better announcement without any change**. No parameters were added, removed, or made required: `semanticsLabel`, `automationKey`, and `semanticHint` remain optional and nullable, and the change is fully backward compatible.
* **New `LiveAnnouncer` component** (`lib/component/live_announcer.dart`, exported from `package:fabric_flutter/fabric_flutter.dart`). A small, generic helper for announcing transient state — "3 results found", "Saving…", connectivity changes — that never receives focus and would otherwise be silently missed by assistive technology. It combines a `Semantics(liveRegion: true)` node (the preferred, non-disruptive, platform-idiomatic mechanism) with `SemanticsService.sendAnnouncement` (which works even when nothing visible changed but is disruptive on Android), and **deduplicates**: the message is announced only when it actually changes, so rebuilding a hundred times with the same message announces once. A `null`, empty, or whitespace-only message announces nothing and is not an error, and also resets deduplication so restoring the previous message announces it again. Announcements are dispatched after the current frame and guarded by a `mounted` check, so an announcer disposed mid-frame never announces. Signature: `LiveAnnouncer({Key? key, required String? message, Widget? child, Assertiveness assertiveness = Assertiveness.polite, bool announce = true, bool liveRegion = true, bool announceOnMount = true})`. The optional `announceOnMount` flag (default `true`, preserving the announce-on-mount behavior) can be set to `false` to suppress the first announcement and speak only on subsequent transitions — useful when the widget is mounted with a message that reflects already-present state; when `false` the deduplication state is seeded with the current message, so a later change to a different message still announces while a rebuild with the seeded value stays silent. `announceOnMount` is purely additive and non-breaking: the default leaves every existing call site announcing on mount exactly as before.
* **`LiveAnnouncer` can now announce repeated events (`announcementTag`).** `LiveAnnouncer` deduplicates identical consecutive messages, which is correct and load-bearing for **state** ("3 results found" can rebuild a hundred times and must be spoken once) but wrong for **events**: two taps on *Send* are two distinct occurrences that happen to share the label "Message sent", and the second announcement was silently dropped, leaving screen-reader users with no confirmation that the second send happened. Consumers were working around this downstream by keying the widget on a counter (`ValueKey(sendAttempt)`) to force a state reset. The new optional `announcementTag` (`Object?`, defaults to `null`) makes the deduplication key the pair `(message, announcementTag)` instead of `message` alone: an identical message paired with a **new** tag announces again, an identical message paired with the **same** tag is still suppressed, and a `null` tag reproduces today's message-only deduplication exactly. A tag is used rather than a `forceRepeat` flag on purpose — a flag cannot distinguish a new event from an incidental parent rebuild, so it would reintroduce the spam the deduplication prevents, while a tag ties re-announcement to an explicit caller-owned event identity. It composes with `announceOnMount: false` (mount seeds both the message and the tag, so a mount-silent announcer stays silent) and with the blank-message reset path (a `null`/empty/whitespace message still clears the state). Purely additive and non-breaking: `LiveAnnouncer({Key? key, required String? message, Widget? child, Assertiveness assertiveness = Assertiveness.polite, bool announce = true, bool liveRegion = true, bool announceOnMount = true, Object? announcementTag})`. The state-versus-event distinction is now documented in the class dartdoc with a worked example.
* **Opt-in operating-system text scaling for `InitApp`.** `InitAppChild` (`lib/component/init_app.dart`) continues to render the application with `TextScaler.noScaling` by default, so **upgrading changes nothing about text sizing on any platform**. Disabling the OS text scale is deliberate: honoring it caused a layout bug on iOS, and consuming applications are sized against the fixed-scale behavior. The rationale is now documented at the call site so it is not removed by mistake. Applications that want the standard Flutter behavior can opt in with the new `InitApp`/`InitAppChild.honorSystemTextScale` flag (defaults to `false`), optionally tuning the new `minTextScaleFactor` (`kDefaultMinTextScaleFactor`, `1.0`) and `maxTextScaleFactor` (`kDefaultMaxTextScaleFactor`, `1.4`) bounds, which apply only when the flag is enabled; passing `null` to both opts out of clamping entirely. The clamping logic is exported as the standalone `clampedTextScaler` helper. Opting in is at the host application’s own risk and should follow a visual pass over every screen, especially on iOS.
* **Images and avatars are now labelable.** `SmartImage` gained the package's standard `semanticsLabel` / `automationKey` / `semanticHint` trio plus an `excludeSemantics` escape hatch for purely decorative imagery, and its loading (`downloading`) and error (`image_not_supported`/`broken_image`) placeholders announce localized state. `UserAvatar` exposes the same trio, defaults `semanticsLabel` to the user's resolved display name, forwards it into the `SmartImage` it renders, and merges the avatar, name, and presence indicator into a single announced node. All parameters are optional and nullable.
* **`Breadcrumbs` is now a navigation landmark (WCAG 2.4.8).** The trail is wrapped in `Semantics(container: true, label: ...)`, the current crumb is marked as the current location, each interactive crumb is exposed as a labeled button (non-interactive crumbs are not announced as buttons), and the `/` dividers are excluded from the semantics tree.
* **Icon-only controls have accessible names.** Added tooltips or `Semantics` labels to previously unlabeled controls in `connection_status`, `alert_data`, `expansion_table`, `logs_list`, `google_chart_container`, `filter_menu`, `json_explorer_search`, `edit_save_button`, `user_admin`, `upload_image_media`, `input_data` (the show/hide-password toggle), `flag_chip`, and `user_chip`.
* **Status changes are announced.** `SemanticsService` announcements were added for connection lost/restored (`connection_status`), alert appearance (`alert_data`), page transitions (`pagination_nav`, `pagination_container`), upload success (`upload_image_media`), dictation start/stop (`voice_dictation_button`), and authentication failures and step changes (`view_auth_page`). Announcements fire only on real transitions, never on every rebuild.
* **Forms surface errors and follow a logical focus order.** Radio inputs in `input_data` now render through `InputDecorator` so their label and `errorText` are visible and announced (validation failures were previously invisible for radio fields); `profile_edit` converted snackbar-only name validation to inline `errorText`; `update_password`, `profile_edit`, and `user_add_update` chain `textInputAction` for a sane focus order; and the verification-code field in `view_auth_page` gained `AutofillHints.oneTimeCode`.
* **Groups announce as groups.** Single-select options expose `inMutuallyExclusiveGroup` and `selected` (radio and dropdown suggestions in `input_data`, steps in `stepper_extended`), and option lists and filter chip sets carry a container label so their purpose is announced once instead of per option.
* **Assistive-technology preferences are respected.** `Tabs` disables its indicator animation under `MediaQuery.disableAnimationsOf`; `PaginationContainer` renders an explicit "load more" button instead of relying on scroll-edge detection when `MediaQuery.accessibleNavigationOf` is true; `AlertData` extends the visible duration of critical alerts for screen-reader users; and `ViewFeatured` skips its staged reveal so content is not hidden-but-present.
* **Tap targets and landmarks.** Enlarged sub-48×48 tap targets (`expansion_table` expand/collapse, `json_explorer_search` copy, `pagination_nav` arrows, `upload_image_media`), marked headings with `Semantics(header: true)` (`section_title`, `route_page`, `view_auth_page`, `view_featured`), gave raw map views a text alternative (`google_maps_preview`, `google_maps_search`), and exposed bare `GestureDetector`/`InkWell` handlers as labeled buttons.

New localization keys were added to `lib/placeholder/default_locales.dart` with English and Spanish translations.

### Performance
* Fixed `StateShared.dispose()` never cancelling its debounced *data* timer (`lib/state/state_shared.dart`). `dispose` cancelled `_timerNotify` but not `_timerData`, so a state disposed inside the debounce window left a pending `Timer` that later fired `_controllerStream.sink.add(...)` and `super.notifyListeners()` on an already-disposed `ChangeNotifier` with a closed `StreamController`. Both timers are now cancelled.
* **Fixed `StateDocument`, `StateCollection`, and `StateAPI` never cancelling their active `StreamSubscription` on disposal.** None of the three subclasses overrode `dispose()`, so a Firestore snapshot listener (document or collection) or an HTTP JSON-stream subscription started by `listen()` stayed alive after the owning widget was torn down. Each snapshot or stream event that arrived afterwards called `notifyListeners()` on a disposed `ChangeNotifier`, which Flutter treats as a programming error. All three classes now override `dispose()` to cancel and null the subscription before calling `super.dispose()`. `StateDocument` and `StateCollection` also rename their internal subscription field from private to `@protected streamSubscription` so concrete subclasses and test helpers can assign a subscription set up through a mock transport without importing Firestore types.
* **Fixed four post-dispose and build-phase lifecycle defects in `StateShared` (`lib/state/state_shared.dart`).** (1) `notifyListeners()` lacked a disposed guard, so any call after `dispose()` scheduled an uncancellable `Timer` whose callback then invoked `super.notifyListeners()` on a disposed `ChangeNotifier`, tripping Flutter's `debugAssertNotDisposed` and throwing in every widget test. (2) The `error` setter and `_publishData()` each called `_controllerStream.sink.add(…)` on a `StreamController` already closed by `dispose()`, throwing `Bad state: Cannot add event after closing`. (3) `applyFilters()`'s fetch path scheduled a `Future.delayed(400ms).whenComplete(call)` with no `mounted` guard, while the structurally identical redirect path immediately below it correctly guarded with `if (!context!.mounted) return;` — an asymmetry that is an evident oversight. (4) Both synchronous-dispatch paths in `notifyListeners()` and `_publishData()` (active when `debounceTime <= 0`) called `super.notifyListeners()` during the Flutter build phase, throwing `setState() or markNeedsBuild() called during build`. For (1)–(3), `dispose()` now sets a `_disposed` flag checked by `notifyListeners()`, `_notifyData()`, `_publishData()`, `set error`, and the fetch callback; a `kDebugMode` diagnostic is emitted on the (1) path so callers who caused the notify after dispose can detect it. For (4), both immediate-dispatch paths detect `SchedulerPhase.persistentCallbacks` and defer via `addPostFrameCallback`, with the deferred callback re-checking `_disposed` because post-frame callbacks cannot be cancelled. The deferred notification settles after one extra rebuild because the `error` setter's existing change-guard (`if (_error == errorMessage) return`) suppresses the duplicate on the second build. No public API was changed and no existing behaviour outside the after-dispose and build-phase cases is affected.
* De-duplicated the memoized `serialized` implementations in `StateUser` and `StateUsers` onto the new shared `StateShared.cachedSerialize` helper (see **Added**), removing two independent copies of the same cache/token/flag bookkeeping. Behavior is unchanged, including the existing error paths, which still retry on the next read rather than caching a failure.
* Marked the two `Spacer` instances in `LoadingScreen` (`lib/placeholder/loading_screen.dart`) as `const` so they are allocated once instead of on every build.
* Fixed the N+1 Firestore read pattern behind `UserChip` (`lib/component/user_chip.dart`, `lib/state/state_users.dart`). `StateUsers.getUser` issued one `.get()` per uncached identifier and called `notifyListeners()` once per resolved document (after an artificial 500 ms delay), and `UserChip` called it from `build()` — so rendering a list of N chips produced N document reads and N full-list rebuilds, started from the render phase. Identifiers requested during the same frame are now coalesced into a single batch, resolved with chunked `whereIn` queries (30 per query, the Firestore limit), and produce exactly one `notifyListeners()` once the batch settles. A pending/in-flight guard ensures the same identifier is never read twice. `UserChip` now requests from `initState`/`didUpdateWidget` and only reads the cache in `build`. **Backwards compatible:** `getUser` keeps its signature and still returns a placeholder synchronously; the new `prefetchUsers`, `cachedUser`, `chunkUids`, `whereInLimit`, and `flushPendingUsers` members are purely additive.
* Fixed `InitAppChild` (`lib/component/init_app.dart`) registering a **new, never-cancelled** `StateUser.streamStatus` subscription on every `build()`. Because the widget was a `StatelessWidget` and the `StreamSubscription` was discarded, every rebuild stacked another listener on top of the previous ones, so analytics `setUserId` and the whole `StateNotifications` init/`getUserToken` sequence re-ran once per accumulated subscription for every `UserStatus` event. `InitAppChild` is now a `StatefulWidget` that subscribes once in `initState`, stores the subscription, and cancels it in `dispose`. The one-shot `WidgetsBinding.addPostFrameCallback` that called `StateGlobal.init()`/`StateUser.init()` moved to `initState` for the same reason.
* Fixed `InitAppChild` forcing a **complete teardown and rebuild of the entire application subtree on every rebuild**. The wrapper's key was `ValueKey('init-app-child-${status?.signedIn}-$now')` where `now` was `DateTime.now().millisecondsSinceEpoch`, so the key was different every single time and Flutter unmounted and recreated every descendant widget — discarding all their `State`, scroll positions, controllers, and re-running every `initState`. The key is now `ValueKey('init-app-child-${status?.signedIn}')`, which preserves the intended behavior (rebuild the subtree when the sign-in state flips) without the per-frame churn. The wrapper is also a `KeyedSubtree` instead of a `Container`, removing a redundant render object.
* Fixed `StateShared.data`'s de-duplication guard never actually firing for Firestore and HTTP payloads (`lib/state/state_shared.dart`). The guard compared with `==`, which is *referential* for `Map` and `List`, and Firestore allocates a fresh map/list for every snapshot — so every snapshot, identical or not, notified every listening widget in every consuming app. The setter now compares structurally with `DeepCollectionEquality` behind an `identical()` fast path, so a snapshot that renders identically no longer triggers a rebuild.
* Moved image decoding, resizing, and encoding off the UI isolate in `MediaHelper` (`lib/helper/media_helper.dart`). `resize()` and the camera capture path called `img.decodeImage`, `img.copyResize`, `img.encodeJpg`, and `img.encodePng` synchronously on the main isolate, freezing the UI for the duration (hundreds of milliseconds for a multi-megapixel photo). The work now runs through `compute()`, with the same web/failure fallback pattern already used by `StateAPI` for streamed JSON parsing.
* Fixed `PaginationContainer` (`lib/component/pagination_container.dart`) leaking its stream subscription. `initState` discarded the `StreamSubscription` returned by `listen()`, and `dispose` called `stream.drain()` — which attaches a *second* listener rather than releasing the first one — so the original subscription kept processing events after the widget was unmounted. The subscription is now stored and cancelled in `dispose`.
* Hoisted the per-build filtering and sorting out of `FilterMenu.build` (`lib/component/filter_menu.dart`). Two `O(n log n)` sorts plus a `FilterHelper.filter` pass and an option-mapping pass ran on every build — which for a filter menu means every keystroke, every chip toggle, and every ancestor rebuild. They now run in `_recomputeOptions()`, invoked only from `initState`/`didUpdateWidget`/`didChangeDependencies` when the filter collection actually changes; `build` only copies the cached active list before mutating it.
* Replaced `Query.parameters.toString().hashCode` comparisons in `StateCollection` (`lib/state/state_collection.dart`) with a structural `DeepCollectionEquality` check. Stringifying and hashing was both more expensive on large `whereIn`/`arrayContainsAny` payloads and collision-prone — a hash collision would leave a stale Firestore listener attached when the query had genuinely changed.
* Added equality guards to setters that previously notified unconditionally: `StateViewAuth.phone`, `phoneVerificationCode`, `verificationId`, and `section` (`lib/state/state_view_auth.dart`), and `StateShared.selected` (`lib/state/state_shared.dart`). These are commonly re-assigned per keystroke or from a parent rebuild with an unchanged value, and each redundant `notifyListeners()` fans out to every listening widget in every consuming app.
* Narrowed over-broad `MediaQuery.of(context)` dependencies to the specific aspect being read: `MediaQuery.platformBrightnessOf` in `InitAppChild` and `MediaQuery.devicePixelRatioOf` in `SmartImage` (`lib/component/smart_image.dart`). `MediaQuery.of` subscribes to the entire `MediaQueryData`, so both widgets previously rebuilt on every resize, rotation, text-scale change, and safe-area change.
* Narrowed the bare `import 'dart:io'` directives in `lib/variables.dart`, `lib/component/google_maps_preview.dart`, `lib/state/state_user.dart`, `lib/helper/media_helper.dart`, and `lib/helper/firebase_storage_helper.dart` to `show Platform` / `show File`, so web builds and tree-shaking only pull in the symbol that is actually used.

### Fixed
* Fixed `GoogleChartContainer` (`lib/component/google_chart_container.dart`) inflating the vertical range-slider maximum on every rebuild. The bounds guard read `if (min >= min)` — a comparison of `min` with *itself*, so it was unconditionally `true` — and therefore ran `max += (min + 100)` on every `reset()`. Because `reset()` is called from both `initState` and `didUpdateWidget`, a chart configured with, say, `min: 10, max: 200` rendered a slider that topped out at `310` instead of `200`, and the ceiling drifted further on each parent rebuild. The comparison is now `if (min >= max)`, which is what the branch was always meant to express: only widen the upper bound when the supplied range is empty or inverted. The normalization was extracted into a pure, top-level `chartRangeBounds({num? min, num? max})` helper — following the same pattern as the existing `chartRangeLabel` — so it can be verified without rendering the webview-backed chart, and is now covered by tests.
* Fixed `InputData` (`lib/component/input_data.dart`) disposing a `TextEditingController` it does not own. `textController` is assigned `widget.textController ?? TextEditingController()`, but `dispose()` called `textController.dispose()` unconditionally, destroying a controller that the *parent* created and may still read from or reuse after the field leaves the tree — any subsequent access throws `A TextEditingController was used after being disposed`. The adjacent `searchController` already had the correct ownership guard; the text controller now has the same one, so only internally created controllers are disposed. Covered by a regression test.
* Fixed `Tabs` (`lib/component/tabs.dart`) keeping a stale `TabController` when the number of tabs changes. The controller's `length` was fixed once in `initState` with no `didUpdateWidget`, so a parent that added or removed a tab left the controller describing the old count and tripped a framework assertion inside `TabBar`. The controller is now rebuilt when `tabs.length` changes, preserving the selected index. Separately, `build()` assigned `_tabController.index = widget.tabs.indexWhere((e) => e.selected)`, which is `-1` when no entry is marked selected — not a valid index — so a tab list with no explicit selection threw; the index is now clamped and skipped entirely for an empty list. The state moved from `SingleTickerProviderStateMixin` to `TickerProviderStateMixin` because recreating the controller requires a second ticker. Covered by tests.
* Fixed `ViewFeatured` (`lib/view/view_featured.dart`) leaking four of its five animation timers. All five staged `Timer`s were assigned to a single `_timer` field, so each assignment orphaned the previous one and `dispose()` could only cancel the last — the other four kept running against an unmounted state. Compounding this, `animationTrigger()` was invoked from `didChangeDependencies()`, which fires again on *every* inherited-widget change (theme, locale, media query, text scale), so each of those spawned five more timers and restarted the reveal animation mid-flight. Timers are now tracked in a list, cancelled both before a re-trigger and in `dispose()`, and the sequence starts once from `initState`.
* Fixed `ConnectionStatus` (`lib/component/connection_status.dart`) registering a new auto-dismiss callback on every build. `WidgetsBinding.instance.addPostFrameCallback` was called from inside the `StreamBuilder` builder, so every rebuild stacked another pending 10-second dismissal; each one checked `mounted` *before* its `await` but not after, so `setState` could fire on a disposed state. The dismissal is now a single cancellable `Timer` that is replaced when the banner reopens, re-checks `mounted` when it fires, and is cancelled in `dispose()`.
* Fixed `RoutePage` (`lib/component/route_page.dart`) invoking `onContextReady(context)` directly from `build()`. Consumer side effects — navigation, provider writes, analytics — therefore re-ran on *every* rebuild rather than once when the context became usable, and running them during the build phase is illegal for anything that triggers a rebuild. The callback now fires from a post-frame callback, latched so it runs once per not-ready → ready transition and re-arms if `status` goes back to not-ready. **Behavior-visible to consumers** that relied on the repeated invocation.
* Fixed `BuildContext` use across async gaps throughout the package, and re-enabled the lint that detects it (see *Changed*). Every site now guards with `context.mounted` before presenting an alert, navigating, or reading an inherited widget after an `await`: `ProfileEdit` (both `catch` blocks after the `user-actions-update` callable, and the avatar-picker failure path), `GoogleMapsSearch` (place-search and place-details failures — the `onError` callback still fires either way), `UserAddUpdate` (success alert and `Navigator.pop` after `onConfirm`), `UserAdmin` (all three remove-user outcomes), `AlertData` (post-action dismissal and navigation, which also silently fell back to a stale context), `FirebaseStorageHelper` (both upload flows, whose duplicated error branches were consolidated into one guarded helper), `StateShared.setFilters` (the 400 ms delayed redirect), and `ViewAuthPage` (14 sites across phone, Google, Apple, and anonymous sign-in, plus the policies dialog). Previously any of these could throw or act on a defunct element if the user navigated away mid-request.
* Fixed `RegexHelper.urlStrict` rejecting every top-level domain longer than 6 characters, such as `.digital`, `.services`, `.technology`, and `.photography`. The `{1,6}` cap was inherited from the legacy unanchored `RegexHelper.url`, where the trailing character class silently absorbed the overflow past 6 characters; once the pattern was anchored with `$`, the `\b` after the TLD label made the cap a hard rejection instead. The quantifier is now `{2,63}` — 2 being the real-world minimum and 63 the DNS maximum label length — which is strictly more correct than `{1,6}`. Every rejection the anchoring was introduced for is preserved. This also fixes `InputValidation.isUrlValid` and `InputValidation.validateUrl`, the only consumers of the pattern, which would otherwise have rejected customers on those domains. The legacy `RegexHelper.url` is unchanged.
* Removed a dead index-renumbering statement in `FilterMenu.build` (`lib/component/filter_menu.dart`). `activeOptions.map((e) => e.index = activeOptions.indexOf(e));` used a lazy `map` with no terminal operation, so it never executed. It was replaced with a comment rather than enabled, because enabling it would be incorrect: it mutates shared `FilterData` instances from `build`, assigns `0` to the first entry even though `FilterHelper` treats a non-positive `index` as "unset", and renumbers the locally constructed sort chip instead of the instance held in `data`. Rendering order already comes from the sort in `_recomputeOptions`, so behavior is unchanged.
* **Fixed a buggy URL validation pattern.** `RegexHelper.url` is **unanchored**, so it reported a match for any string that merely *contained* something URL-shaped — `'garbage https://example.com'`, `'xhttps://example.com'`, and `'https://example.com trailing junk'` all passed. That made it unsuitable as a form validator, which is how `InputValidation.isUrlValid` (and therefore `validateUrl`) was using it. Added the anchored `RegexHelper.urlStrict` (`^https?://...$`) and switched `InputValidation.isUrlValid`/`validateUrl` over to it. **This is an intentional behavior change:** those three inputs now correctly fail validation. Every genuinely well-formed URL that passed before still passes — verified against `https://example.com`, `http://example.com/path`, `https://example.com/a?b=c#d`, and `https://sub.example.co.uk/x`. `RegexHelper.url` itself is unchanged and still exported for backwards compatibility, but is now documented as a contains-a-URL pattern that should not be used for validation.
* Fixed `MediaHelper.getFile` (`lib/helper/media_helper.dart`) throwing `UnsupportedError` on web when a video was selected. The video-dimension probe called `File.fromRawPath` — a `dart:io` API with no web implementation — without a `kIsWeb` guard. The probe is now skipped on web, where raw-byte dimension extraction is not possible anyway.
* Fixed `VoiceDictationButton` triggering iOS `error_unknown (300)` (`kAFAssistantErrorDomain`) when a new press started a fresh recognition session before the previous session's `stop()` had finished tearing down on the platform side. The widget now guards against re-entrant starts and awaits the pending `stop()` before requesting a new `listen()` session.
* Fixed `VoiceDictationButton` surfacing `error_unknown (300)` (and similar iOS teardown noise) as a user-facing error even when the button was no longer pressed. `speech_to_text` only honors the `onError`/`onStatus` callbacks passed to the *first* `initialize()` call for the lifetime of its singleton — every later call is a no-op — so the same error listener kept receiving delayed native teardown events from already-stopped sessions. The listener now discards any error that doesn't correspond to a session currently being requested or actively listened to.
* Fixed `VoiceDictationButton` still surfacing `error_unknown (300)` even after the above fix, because the native session can also emit this code while the button is genuinely still being held (e.g. the platform's own end-of-utterance/pause detection ends the recognition task "unsuccessfully" before the user releases). `kAFAssistantErrorDomain` code 300 (like Android's equivalent catch-all) is simply the platform's generic "task finished without a match" signal, not an actionable failure — the underlying package itself only maps a handful of codes (permission/config/network/assets) to anything specific. `_handleError` now classifies error messages: benign end-of-session codes (`error_no_match`, `error_speech_timeout`, `error_busy`, `error_client`, `error_retry`, `error_request_cancelled`, `error_speech_recognizer_already_active`, `error_speech_recognizer_connection_invalidated`/`_interrupted`, and any unmapped `error_unknown (*)`) are now fully ignored; only genuinely actionable errors (permission denied, disabled recognizer, missing assets, network/server failures, unsupported locale) are still forwarded via `onError` and stop the session.
* Fixed `VoiceDictationButton` appearing to stop listening the instant the button was pressed. The previous benign-error fix still called `stop()` for benign codes, and because the persistent error listener has no way to tell which session an event actually belongs to, stale `error_unknown`/`error_no_match`-style noise from the *previous* session frequently arrived right as a new session was starting, immediately ending it. Benign errors are now fully discarded — neither reported nor treated as a reason to stop — so a fresh press-and-hold session is no longer interrupted by leftover teardown noise from the last one.
* Fixed `VoiceDictationButton` going silent (mic still showed "listening" but no further transcripts/callbacks ever arrived) after the previous fix, because on some devices `error_unknown (300)` genuinely reflects the *current* recognition task ending (e.g. the platform's own end-of-utterance/pause timeout) rather than stale noise, and fully ignoring it left `_listening` stuck `true` with a dead recognizer underneath. `_handleError` now transparently requests a fresh `listen()` task when a benign error arrives while the button is still held, instead of doing nothing, so dictation keeps going without the caller ever seeing a gap. Because each new task starts fresh recognition, already-recognized words are now committed into an accumulator before restarting so `onPartialTranscript`/`onFinalTranscript` keep reporting the full combined transcript across the restart instead of only the newest segment.
* Fixed a possible silent infinite-restart loop introduced by the auto-restart fix above: if the recognizer keeps ending benignly on every single restart attempt without ever producing one real result (e.g. a broken audio route/permission state that fails the same way every time), the button would appear stuck "listening" forever while never reporting any transcript or telling the caller why. After 3 consecutive benign restarts without a result, the error is now finally surfaced via `onError` and the session stops instead of retrying silently forever; any real result resets the counter.
* Fixed `VoiceDictationButton` letting an exception thrown by a caller-supplied callback (`onPartialTranscript`, `onFinalTranscript`, `onListeningChanged`, `onAvailabilityChanged`) propagate and crash the recognizer lifecycle. Every callback invocation is now wrapped and any failure is routed to `onError` instead (a throwing `onError` itself is caught and only logged via `debugPrint` under `kDebugMode`, since there is nowhere further to report it).
* Applied the same callback-safety pattern across the rest of the package wherever an external callback is invoked from code we control (async/listener contexts, not synchronous Flutter gesture dispatch which the framework already protects):
  * `StateShared` (`lib/state/state_shared.dart`, the base for `StateDocument`/`StateCollection`/`StateAPI`/`StateUsers`) now guards its `callback` and `onError` invocations — a throwing `callback` or `onError` no longer prevents `notifyListeners()`/`stream`/`streamError` from still publishing the update, and is only logged via `debugPrint`/`LogColor` under `kDebugMode`.
  * `PaginationContainer` and `StepperExtended` now guard their `onScrollOffsetChanged` scroll-listener callback so a throwing callback can no longer skip the pagination-detection logic that runs after it in the same listener. Both widgets now expose a new optional `onError` (`ValueChanged<String>?`) so consumers have a dedicated place to receive these (and other internal) errors instead of only a debug log; `PaginationContainer.onError` also now receives `paginate()` and stream failures that previously were only reflected in the inline error footer.
* Fixed `StepperExtended` never actually reporting scroll offset changes: `build()` created a second, unrelated `ScrollController` for the visible `SingleChildScrollView`/`Scrollbar` instead of reusing the `_controller` field that `onScrollOffsetChanged` was registered against, so the listener was permanently dead code. Both now share the same controller.

### Changed
* Made the `context` argument of `alertData` and `dismissAlerts` (`lib/component/alert_data.dart`) **optional**, and consolidated context resolution into a single new public helper, `alertContext(BuildContext?)`. `alertData` was already internally context-safe — it early-returns on a null or unmounted context — but `use_build_context_synchronously` fires on *referencing* a `BuildContext`-typed expression after an async gap and has no way to know the callee is safe. Every post-`await` `alertData(context: context, ...)` was therefore flagged despite being harmless, which pushes callers toward pointless `mounted` guards, `// ignore:` comments, or disabling the lint outright (exactly what this package had done). The fix is to stop passing a context at all: **after an `await`, call `alertData(...)` without a `context` argument** and it resolves the root context through `AppGlobal.navigatorKey`. This is not just lint appeasement — it is strictly better behavior, because the previous code *dropped* the alert when the caller's element had been unmounted, whereas the fallback still shows it. `alertContext` prefers a supplied mounted context, falls back to `AppGlobal.navigatorKey.currentContext`, and returns `null` only when neither exists, in which case the alert degrades to a `debugPrint` and returns without throwing. The three ad-hoc `AppGlobal.navigatorKey.currentContext ?? context` fallbacks previously scattered through the file now route through it. **Source-compatible:** `context` stays nullable and every existing call site that passes it keeps working unchanged — relevant given the consumer app has 259 `alertData(` call sites. Consumers must assign `AppGlobal.navigatorKey` to `MaterialApp.navigatorKey` (and `AppGlobal.snackbarKey` to `scaffoldMessengerKey`) for the contextless path to render UI; without that wiring it degrades to a log. Covered by tests.

### Added
* Added `StateShared.cachedSerialize<T>(Object? source, T Function() build)` and the companion `invalidateSerialized()` (`lib/state/state_shared.dart`), a reusable memoization scaffold for the `serialized` getter. `serialized` is read many times per update — once per listening widget build plus any internal consumers — while `data` is replaced by a brand new object on every fetch, so every read previously re-ran the full `fromJson`/sort/filter conversion. `cachedSerialize` returns the previously built value while the `source` stays *identical* (reference equality, so the cache cannot go stale) and rebuilds as soon as a new payload is assigned; `clear()` invalidates it automatically. `null` sources are cached like any other value, and an exception thrown by `build` propagates while leaving the previous cache entry untouched. This replaces the hand-rolled `_serializedCache`/`_serializedCacheToken`/`_serializedCached` triple that `StateUser` and `StateUsers` each carried, and is available to every downstream state class. **Purely additive** — existing subclasses that do not call it are unaffected.
* Added an opt-in edit/revert lifecycle to `StateDocument` (`lib/state/state_document.dart`): `edit`, `copy`, `editField()`, `revert()`, and `save()`. Setting `edit = true` captures a shallow snapshot of `data` into `copy`; `editField(key, value)` applies a local unsaved change by *replacing* the payload (a direct `data[key] = value` mutation would be structurally indistinguishable from the previous value and would never notify listeners); `revert()` restores the snapshot and leaves edit mode; `save()` writes the payload — minus the `id` key, which is the document key rather than a stored field — and only exits edit mode after the write succeeds, so a failed save leaves the user's changes on screen while recording the failure through `error`. `clear()` resets both the flag and the snapshot. **Purely additive and non-breaking:** all members have defaults, and existing `StateDocument` subclasses that ignore them behave exactly as before.
* Added `clientFactory` to the `StateAPI` constructor (`lib/state/state_api.dart`). `StateAPI` recreates its `http.Client` after every request to avoid stale persistent connections, which previously discarded any injected client after the first call and made a second request unavoidably hit the network. Supplying a factory keeps a custom transport in place across those resets. `httpClient` and the existing constructor signature are unchanged; omitting `clientFactory` produces the previous behavior exactly.
